On the discipline of the craft · 2025

I did not choose code because it was fast. I chose it because it was patient. It rewards the one who returns to the same small problem the next morning — sits down, and begins again. My practice: take the complex system, the one that updates twenty times a second, the one people depend on at 3am — and make it feel calm. That is the whole work. Everything else is decoration. And decoration, as any monk will tell you, is where the ego hides.

    戒 Scroll Three

    The precepts I keep.

    A monk keeps vows. Not because they are rules — but because they are a frame for attention. These are the five I return to every time I open an editor.

    簡

    Prefer less, not more.

    The smallest change that solves the problem is almost always the right one. Every line you don't add is a line someone won't have to read at 2am.

    — Because code is read far more often than it is written.

    遅

    Move slowly, ship deliberately.

    Speed in the editor is not the same as speed to the user. I'd rather take a day longer than fix a rushed interface for a month.

    — Because the rush you feel is not the user's rush.

    明

    Name things truly.

    If a function is hard to name, it is doing too much. If a component resists a name, the boundary is wrong. Naming is design work.

    — Because a good name is half the documentation.

    静

    Make the quiet version.

    Interfaces should not shout. No gratuitous animation, no gratuitous colour, no ornament that doesn't earn its place. The best UI is forgotten.

    — Because attention is the user's scarcest resource.

    受

    Accept critique without flinching.

    Every code review is a gift from someone who owes you nothing. The ego wants to defend. The craftsman wants to learn.

    — Because a defended mistake is a doubled mistake.

    修 Scroll Six

    The four practices.

    一

    Listen to the problem

    Before one line of code, I want the shape of what success looks like. What hurts today. What we're deliberately not doing. Most projects fail here, not in execution.

    二

    Prototype in the real thing

    Figma is where we agree. Production is where we learn. I prototype in Next.js early so we can feel the actual latency, hit real APIs, and make honest tradeoffs.

    三

    Sweat the milliseconds

    Bundle budgets, render timing, skeleton states, error boundaries, animation easing. The unglamorous work that makes a product feel expensive. It compounds.

    四

    Hand it over well

    Readable code, honest docs, a working demo. I'd rather ship something a team can extend than something only I understand — the mark of a true craftsman.
